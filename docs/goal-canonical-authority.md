# Canonical Goal authority adapter — separate source slice

Current-source successor: [goal-current-assembly.md](goal-current-assembly.md) now attaches this unchanged adapter to the actual server services once; the original slice's independent scope and remaining host-proof constraints below still apply.

`GoalCanonicalAuthority` implements the existing broker binding and server action-hook shapes using the same `CompanyService.store`, actual current session registry, retirement projection and owner service. It performs no initialization, store write, generation increment, adoption, grant issuance or migration reconciliation. Missing dependencies/custody deny. The r3 Goal reducer, authentication transport, singleton server registration and their accepted packets are unchanged.

## Sources and policy

- `binding(sessionId)` reads the existing canonical company file through `CompanyStore.snapshot()`, not a parallel state/cache. It requires one unambiguous employee/session, canonical owner and positive existing sessionGeneration, no migration/vacation/intentional stop, plus a matching currently running runtime session not marked retired. It returns that exact generation, unchanged. A broker maintenance counter is never consulted.
- `assertAction(action, principal, request)` is scope admission for an already authenticated principal, not an authentication method. The sealed proof/owner boundary must establish identity first. Method plus registered route template must match. The same canonical source is re-read on every invocation, including canonical commit checks; the real current owner service or exact live employee binding is checked again after scoped work and custody checks.
- Worker READ/CREATE/TRANSITION are limited to the exact owned current employee/Goal binding. Cross-employee TRANSITION requires an existing independent VERIFY grant naming the exact verifier/target sessions and generations, Goal generation and request review sequence, with current expiry/revocation checks. It does not turn VERIFY into full read.
- Cross-employee metadata requires the existing METADATA_READ grant and exact current grantee/target canonical bindings. It never gains objective, evidence or other private fields.
- ADOPT, ISSUE_GRANT, REVOKE_GRANT, ATTEST_UNBLOCKER and REVOKE_PROOF require the genuine current owner path and appropriate existing owned canonical targets. No employee permission bits, coordinator title, Basic/header/service identity or new grant kind are introduced.

These rules derive from Kit's accepted authorization matrix and the accepted r3 authority. The canonical core remains independently authoritative for strict command parsing, legal edges, worker REVIEW freeze, HOLD proof, generation/CAS, owner-only closures/reopen/adoption, historical replay and response visibility. The adapter does not perform a speculative mutation or create a second facade to preview permission. In particular it must admit an exact authorized historical replay to the core even when the present Goal state has advanced.

Actor liveness and target binding are intentionally distinct. A worker/verifier actor must have a live current runtime. As in r3, an owner can inspect/plan/revoke against a still-current canonical target whose runtime is stopped; an authorized live metadata reader can observe that target. Vacation/off/migration and grant/session-generation fences still apply to scoped target authority. This does not launch/recover the stopped runtime or grant execution.

## Composition and remaining boundary

The server-side binding callback is structurally `sessionId => authority.binding(sessionId)`. Its action callback is `(action, principal, request) => authority.assertAction(action, principal, request)`. Use the adapter constructed from the already-owned single CompanyService and actual runtime/owner services, never another CompanyStore or caller-supplied state. Before attachment, the callbacks must refuse. This separate slice does not add a production attachment/configuration hook or enable the normal launcher; safe post-construction server/bootstrap attachment still needs reviewed source composition. Do not deploy the fixture's private casts or synthetic proof/runtime/custody adapters.

This canonical lookup is NOT proof of a fixed host office's generation. The signer must retain its independently established fixed connection/generation capability; neither a broker restart nor this current lookup may silently adopt a stale office into a newer generation. Real authenticated host-to-server binding delivery/bootstrap is still absent. No signer, issuer/key/epoch reader, custody authority or nonce provisioning is added.

The named app.inject fixture uses one actual CompanyService/GoalLifecycle, owned synthetic company/auth files, the real owner service and real canonical action/binding implementation. Proof transport, runtime observations and custody are explicit synthetic fixtures; they are not a live isolation/custody claim. Independent review and combined source integration, accepted nonce repair, actual host trust/custody provisioning, migration reconciliation, native build/image and authorized canary/rollback proof remain required. No host/model/network/engine or live Goal operation occurs here.
