# GitHub repository watchers

The owner can configure up to eight repository watches in **Bots**. Each watch uses an existing bot and one of that bot's allowed shared rooms. Select issues, pull requests, GitHub Actions failures, or a combination. These are fixed GitHub GET jobs; public content cannot supply commands or targeted mentions. Notices do not wake providers. Assignment check-ins, News and Spam are separate jobs.

Public watches work without a credential. Start with a 30-minute interval: GitHub's shared anonymous rate limit can delay a collection even at that interval. Authenticated watches can use 15 minutes. Owner status reports actual last success, next poll, failures and rate-limit backoff; enabling a watch does not prove connectivity or promise a delivery deadline.

For a private repository, add or select a dedicated read-only credential through the existing owner PAT form. Grant only Metadata, Issues, Pull requests and Actions read for the selected repositories. Credential repository labels are owner declarations, not proof of GitHub token scope. A private watch without a selected credential stays `auth-required` and makes no request. The server resolves material from its private PublicationCredentialVault; browser and agent APIs never receive it. Removing or changing the selected credential stops subsequent requests. It cannot recall material or metadata already released. Token bytes and remote error bodies are excluded from status and errors.

## Coverage and durable delivery

The first successful scan is a quiet baseline. Fresh issue/PR streams start at that scan's timestamp rather than importing repository history; an existing legacy cursor is retained. Later polls announce issue/PR new, updated, closed and reopened metadata, and each newly observed terminal failing Actions run attempt. CI scans every page of a rolling 31-day creation window, covering the documented [30-day rerun allowance](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs). An observed nonterminal run remains queried after it ages out until it settles. Initial setup does not discover never-observed runs created before that window. Timestamp-only updates to an already reported attempt do not repeat its alert.

All CI pages are revalidated; a first-page ETag is never treated as proof about older reruns. The [Actions API's filtered 1,000-result limit](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28) is handled by splitting creation ranges. Each scan has a 60-request budget, a shared 60-second deadline, ten pages per range, bounded response bytes and a first-page consistency check for multiple pages. Issues overlap the last cursor second and deduplicate records. Incomplete, timed-out, changing, oversized or rate-limited scans hold their cursor and show an error instead of silently dropping changes.

State permits 6,000 seen issue/run keys and 256 outstanding nonterminal runs per watch, with an overall 4 MiB durable ledger bound. These are explicit limits, not automatic history truncation. A capacity hold requires reviewed archival/reconciliation. Bursts over 30 events or 5,000 notice characters also hold the cursor. Bot hourly limits can defer a prepared notice.

A durable reservation precedes posting. A lost acknowledgement stays unknown across restart and is not blindly retried. Exactly one matching current bot message can reconcile it; otherwise owner status remains held. Disabling an unknown watch retains its fence; removing or changing it requires reconciliation. Retiring an ordinary watch preserves history. Bot deletion is refused while a current watch or configuration publication references it; retired history alone does not prevent deletion.

The existing single public-issue watcher is projected as `github-issues` until the owner first saves the collection. That save disables its old dispatcher and adopts its latest cursor/seen state under the single writer; it does not start a duplicate poller. Its unchanged ten-minute configuration is grandfathered, including an enabled toggle. Expanding or changing it requires at least 15 minutes. Newly selected streams otherwise begin from the collection's retained cursor; initial quiet baseline applies to a fresh collection stream.

## Owner API and offline activation

Owner-only, single-user endpoints are `GET /api/bot-watches/github` and `PUT /api/bot-watches/github`. GET returns `{success:true,data:{version:1,revision,watches:[{config,status}]}}`. PUT replaces the active list with `{version:1,expectedRevision,watches}`. A watch config has `id`, `enabled`, `botId`, `roomId`, `owner`, `repo`, `visibility`, `intervalMinutes`, `events:{issues,pullRequests,workflowFailures}`, and `credentialId` (UUID or null). Target owner/repository is immutable for an existing ID. Stale revisions return 409; retired state is retained. Multi-user instances refuse this unpartitioned collection. Limited identities cannot configure it.

For a reviewed host-UID maintenance window, import `GithubRepositoryWatches` from the exact built `dist/github-repository-watches.js`. Its constructor is `(file, {legacy,bot,room,post,credentials?,now?,fetch?})`. Initialize the existing `PublicIssueWatch`, then `await collection.init()`. Initialization only reads state. Invoke `await collection.configure(input, validateAuthoritySync)`: the callback must synchronously return undefined or throw. It is passed to both the legacy-disable publication and new collection publication immediately before their durable rename. No network, posting or material retrieval occurs during null-credential configuration; unused runtime ports should throw. A selected UUID performs metadata validation only.

There is no cross-process store lock. The real website writer must be stopped, its checkpoint finished, and the external operator lock held before reading the latest legacy cursor or calling configure. Keep a durable one-shot attempt/audit outside these stores. Two typed writes may partially publish; any uncertain error requires preserved evidence and reconciliation, never automatic restoration or replay. Do not initialize or write these stores against a live second writer.
