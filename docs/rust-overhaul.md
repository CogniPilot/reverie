# Rust overhaul

The target is a Rust core/backend and TypeScript frontend with no first-party
Python and no Python interpreter in the shipped service runtime. This migration
also consolidates deployment, configuration and recovery
behind the [owner GUI/API contract](owner-operations.md). Translating a private
operator script into Rust would retain the architectural problem.

`reverie-owner-terminal-host`. Inline Python in Nix/shell/CI and dynamically
generated launchers must be accounted for before declaring completion.
`python/pyproject.toml` exposes 16 console entry points in addition to fixed
host launchers generated by Nix.

Reproduce the file baseline using the ordinary repository tools:

```sh
git ls-tree -r --name-only 84cadfe9 | rg '\.py$'
git show 84cadfe9:python/pyproject.toml
```

Track Python delivered as an employee programming tool, third-party model
dependencies, and build-time dependencies separately from Reverie's first-party
implementation. Removing first-party Python must not silently remove an owner's
ability to use scientific Python inside an employee laptop.

## Replacement cohorts

| Cohort | Existing code and boundary | Required acceptance |
| --- | --- | --- |
| Memory-limit helper | `soft_limit_helper.py`, `worker_memory_authority.py`; fixed root socket protocol | Duplicate-key/input rejection, root policy custody, peer/PID/cgroup identity, bounded nonblocking write, uncertain effects; Nix selects Rust executable |
| Shared host primitives | Linux file/descriptor custody, process identities, bounded observers and engine metadata | Typed native interfaces, narrowly reviewed unsafe wrappers, race/failure tests; reuse across services without weakening checks |
| Broker and service lifecycle | `worker.py`, `worker_service.py`, transport upgrade/maintenance, resume and watchdog paths | Same admission and desired-running behavior, retained provider continuity, explicit upgrade and rollback/reconciliation; no generic command API |
| Resource operations and storage | `worker_resource_*`, `employee_resource_profiles.py`, `laptop_resource_operations.py`, home/Nix migration | Existing store schema/CAS/locks/leases/reservations, crash recovery, no replay of uncertain effects, no competing source of truth |
| Terminals, devices and scoped Office transport | `owner_terminal_*`, `worker_*` launch/Office/device paths, GPU/browser components | Same scoped grants, peer provenance, terminal/session identity and device selection; no engine socket in clients |
| Memory and agent runtime | `memory.py`, `project_memory.py`, `runtime.py`, `sleep.py`, context/identity/governance and plugin/CLI adapters | Existing SQLite data remains readable, tested write/migration semantics, conversation/account/model behavior preserved, CLI/plugin compatibility |
| Backend application services | Current TypeScript owner/company/plan/resource services | Preserve documented HTTP envelopes, status/error codes, authentication, scoped grants and GUI behavior; one authoritative implementation per operation |
| Numerical/model adapters and tooling | `embeddings.py`, `kokoro.py`, training adapters, build/CI/acceptance tools | Numerical/output compatibility where applicable, measured resource cost, named third-party dependencies and equivalent acceptance coverage |

The narrow helper and active Cargo-default/build-job laptop tools now have Rust
source/package replacements. The workspace uses the shared xtask runner, strict
Clippy and file/spec/script-policy checks. The unused
legacy supervisor was audited and retired rather than recreated as another
control path. Every entry point needs an explicit active/opt-in/retired
disposition; historical file counts are not a mandate to port dead code.

The profile migration includes checked domain types, the existing v1 byte/hash
codec and the private descriptor-anchored profile store. Its library consumers
remain under migration: a profile snapshot alone does not replace configuration
staging, admission, reservations, native effects or reconciliation. Staging must
retain the real profile lock and current employee/storage/grant observations
through its checks, and preserve the separate worker-policy digest format.
The worker client replacement must cover terminal I/O, controls, resource launch
references, telemetry and Goal custody, including streaming custody. Selecting a
native resource client also requires coordinated protected manifests, bootstrap
facts and image provenance; a Rust binary cannot inherit interpreter-shaped
facts or bypass the existing supported activation workflow.

The application resource-staging service now composes profile-store custody,
resource selection and native GPU/perf/memory/lease observations before deriving
the separate profile/config/policy digests. It returns a candidate only. The
current Python broker remains selected until its full worker validation,
admission, reservation, effect and reconciliation consumers migrate. See
[`reverie-application`](../crates/reverie-application/README.md) for the exact
service boundary and compatibility evidence.

The TypeScript resource diagnostics correction remains compatible with the
later Rust backend. Remaining cohorts are pending; no source result here
claims a complete Rust backend or an installed rollout.

## Workspace and quality gate

The [specification index](../spec/README.md) owns the adopted Rumoca rules:
crate layout and DRY in SPEC_0004, complexity in SPEC_0002, valid construction
in SPEC_0006, and thin task orchestration in SPEC_0005. Use the same entry point
locally and in CI:

```sh
nix develop --command cargo xtask verify
```

Use a task-specific `CARGO_TARGET_DIR` under temporary storage. Both Git and Nix
exclude generated Cargo targets. Nix must package the same locked source that
was tested, and CI checks the Rust workspace independently of image publishing.
New Python and shell scripts, including recognized interpreter shebangs and
staged-index conversions, are rejected by the Rust PR workflow under SPEC_0008
while legacy implementations are being retired. The portable gate exercises
core/contracts/xtask on Linux, macOS and Windows; native host adapters have their
separate Linux gate. Neither gate proves unported runtime paths are portable.

Independent adversarial review is required for changed authorization and native
effects. Cover malformed requests, revoked/stale authority, process/path swaps,
partial writes, loss of reply, service death/restart and retained fences. Port
tests with behavior, not just line coverage. Benchmarks must record the exact
baseline/candidate artifacts and comparable workloads; no speedup is claimed
before measurement.

## Removing an old implementation

For each entry point, record the replacement, protocol/data version, relevant
tests, independent findings and package selection. Remove the retired executable
and fallback path from the production package closure. An explicitly labeled
test reference may remain temporarily when needed for differential behavior
checks; it is still migration debt, not evidence of a Python-free tree.

Delete a shared Python module only after every active consumer has migrated.
Preserve durable configuration, histories and uncertain-operation evidence.
Rollout uses reviewed releases and the product's supported operation path, with a
separately authorized native canary. Source checks do not modify a running office.

The overhaul is complete only after every cohort is accepted, owner operations
work through the GUI/API on a fresh installation, first-party Python entry points
and generated code are gone, and the shipped service closure has no Python
interpreter/dependency. Report build-time Python separately rather than confusing
it with the running product. Python an owner installs inside an employee's laptop
remains an owner-selected programming tool.
