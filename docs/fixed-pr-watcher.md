# Fixed public PR notices

Source-only feature; installation, bot/audience configuration and enabling need separate owner/operator acceptance. Nothing here installs a job, selects an audience or reads GitHub during deployment.

An authenticated owner may configure one bot `post` job through the existing cron API. Use `postSource: "github"`, `postSourceArgs: {"owner": "CogniPilot", "repo": "rumoca", "pull": 461}`, `postText: "{message}"`, `postChangeOnly: true`, no condition/kinds, and an interval of at least 15 minutes. The example is the rollout's explicitly selected public target, not a portable hardcoded target. Owner supplies the existing bot and ordinary room IDs; bot allowlist/hourly limits and exact owner scope still apply. Start disabled. Worker/service headers cannot select or override it. No token is needed or accepted.

## Scope and bounds

Only ONE fixed watcher job is admitted in a console, including disabled jobs. Startup execution also refuses duplicate persisted configuration. Case-only target edits preserve deduplication. One console process must be the sole writer of its existing state file: this is NOT a cross-process/repository lock or a claim of repository-wide exactly-once delivery. Other instances must not enable this watcher against the same state. Existing digest jobs are unchanged, including their already-correct query.

Each poll makes at most five anonymous public GitHub GETs under one ten-second deadline: PR, reviews, current-head check runs, current-head workflow runs, and the PR fence again. Redirects and credentials are disabled; each body is capped at 256 KiB before JSON parsing. Public base repository/name/PR identity must match. Wrong-head checks/runs, changing PR head/update fence, decreasing run attempts/times, bad fields, conflicting duplicate IDs, pagination, incomplete counts, full 100-row pages and overflow refuse the poll. Review summaries label historical heads; they are never an approval decision. Snapshot polling is NOT a historical GitHub event stream and cannot recover intermediate states never observed.

Cursor limits: 300 identities, 500 retained event hashes, 120,000 characters, at most 128 new events in a poll. Reader and delivery share the same 128-event / 196,608-character snapshot bounds. This accounts for all 40 known target checks in the first delivery and subsequent mass completion; no initial cursor is silently seeded as delivered. No event eviction: reaching a limit holds the cursor for owner review. Event IDs include target, object identity, attempt and snapshot hash. Cursor retains hashes and fixed metadata only, never review/issue bodies, authors, tokens or raw replies. Up to ten bounded enum summaries are posted; further counted events remain in the receipt. Titles are single-line, mention/markup/control-free and capped. Errors use fixed codes, not upstream response/exception strings. Three pre-effect failures exhaust automatic retries until owner review/config edit; failed polls never look like all-clear.

## Delivery and uncertainty

The existing StateStore main-file writer serializes ordinary/debounced saves and acknowledged watcher commits. A generation-bound bounded pending receipt is atomically written and file/directory-fsynced BEFORE a chat effect. Commit-time generation checks fence edits/disabling during awaits. Ordinary async snapshots cannot overtake a newer intent; acknowledgement failure restores the pending state in memory before another ordinary save. A backup-loaded watcher loses its generation and cannot run, edit or re-enable: an old backup is not evidence that no post happened.

Both constructor fallback and explicit `recoverFromBackup()` use this same watcher fence. Explicit recovery retains newer fixed-watch jobs and their receipt/run evidence even if the backup predates or omits them, disables all recovered/retained watchers and removes their generation. Synchronous recovery refuses while any main-state writer is queued/in flight. Otherwise it cancels pending debounce, clears stale serialization caches, and persists the fenced restoration through the existing writer. A later restart cannot turn restored state into delivery authority. No recovery operation clears uncertainty or permits edit/delete/re-enable/resend without the unavailable separately reviewed reconciliation seam.

The shared backup fence also covers ordinary author/bot posts and session-launch cron jobs. All backup-restored or retained effectful jobs receive server-kept `recoveryUncertain: true`, are disabled, and have no next due time. Current jobs and available completed/uncertain run evidence survive explicit restoration even if omitted by the backup; fallback cannot invent evidence that was lost. Scheduling skips held jobs and Run Now/edit/re-enable/delete return `RECOVERY_UNCERTAIN` before effects. Disable remains available. The request schema cannot set/clear this flag; no same-ID reset or owner reconciliation endpoint exists. Ordinary primary-file restart and normal routine permissions/behavior are unchanged. This is conservative uncertainty refusal, **not general routine recovery completion** or permission to resume from a backup.

Production notices use the existing synchronous SQLite chat commit (FULL synchronous, transaction + archive), not the JSON/debounce fallback. Missing/read-only database, invalid/archived/DM/cross-owner room or bot denial refuses delivery. Notices use `deliver:false`: no agent delivery, owed reply, model request or execution. Only a returned committed chat receipt permits saving the cursor and bounded DELIVERY metadata. A later broadcast/listener error may be ambiguous even if SQLite committed: this intentionally holds rather than resending.

Failed/ambiguous delivery or a crash after intent leaves `watchState.pending` with receipt ID, generation and WATCH_EVENT metadata. Owner job reads/run history expose HOLD and the receipt; disable remains allowed. Edits/delete/run retries cannot erase the pending fence. There is NO automatic resend, clear, reset, cursor advance or re-enable. The visible receipt ID in notice text is diagnostic only, not trusted reconciliation proof.

Owner reconciliation remains HOLD: the existing chat schema has no trusted server-authored structured receipt metadata binding job + generation + pending key + expected sender/room. This release does not broaden client chat fields or add an authority store to invent that proof. Retain the disabled job and receipts for a separately reviewed operator reconciliation; absence in a chat window is never proof of non-delivery. Successful delivery does not automatically re-enable an owner-disabled job.

Goal satisfaction, decision satisfaction, HOLD/security clearing, merging, reruns and all other actions are OFF. Notifications are metadata evidence only. No complete overnight rollout, live activation or general watcher completion is claimed by this source increment.
