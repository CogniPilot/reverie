# Authenticated durable Goal core, successor r3

This source slice repairs the seven grouped findings and nine counterexamples in the independent r1 review. It retains the canonical CompanyStore and human-facing Goal record. The Tim-base successor now registers the effect-free HTTP command boundary against the single GoalLifecycle owned by CompanyService. Registration is not activation: absent trusted server configuration, authentication, custody and action-permission ports deny all Goal reads and writes, including owner requests. No runtime effect adapters are added. See [the actual server integration](goal-server-integration.md).

## Authentication and custody are mandatory

Goal commands never accept an actor, owner, verifier object, principal, credential or grant assertion in the body. A server-composed GoalAuthentication port authenticates the request context, supplies its current principal, and synchronously rechecks credential revocation after asynchronous boundaries and immediately before canonical rename. Employee principals must also match the current employee, exact session, session generation, company and eligibility inside the transaction. Parent-session headers, organizational titles, a shared Basic credential and generic service tokens are not Goal identity proofs.

The included owner adapter validates a real unrestricted owner cookie, owner scope and mutation origin. The separately reviewed broker assertion adapter is an integration dependency, not duplicated here; its real trust/current-binding/custody/durable-nonce ports still require accepted operator implementation and proof. The default adapter denies reads and writes. Even the owner adapter denies access unless the employee adapter's existing trusted custody port proves that the canonical company file, grants, temporary-file directory, lock file and containing namespace are outside worker-writable mounts, and the trusted server configuration explicitly authorizes the current action. A matching uid or mode 0600 alone is insufficient when agents share an account. A request boolean or agent-writable configuration must never supply this proof. Tests inject an explicit synthetic private-store boundary; they establish no host/deployment custody.

The registered module exposes create, current/full read, transition, explicit adoption, owner grant/revocation, owner unblocker attestation/revocation and fixed metadata reads. Actual WebServer setup registers CompanyService.goals, not a second facade. Exact Goal method/registered-route tuples defer the outer policy's decision until after purpose-proof verification and then pass a mandatory authentication/custody/current-action gate, even when normal owner policy is off/log. This is not an AGENT_ROUTES or prefix allowlist; unrelated owner/service/board/routine protections remain. A genuine assertion-free owner cookie uses its own adapter; any mixed owner/proof/parent or service identity refuses. Production worker access stays unavailable without accepted operator ports. Crashed-migration reconciliation remains fenced and unimplemented. No action here sends input, wakes, delegates, delivers, runs a model, touches a host or starts a background loop.

## Authority and lifecycle

Workers may create and advance only their current bound Goal. Worker mutation freezes at REVIEW, including same-state metadata updates. An independent verifier requires an owner-issued canonical grant bound to its own employee/session generation, the target employee/session generation, exact Goal generation, exact REVIEW sequence and expiry. Grant revocation is append-only. The assigned worker cannot be its own verifier. Owner authority remains separate.

HOLD carries a closed category and typed unblocker identity. Resume references an owner-authenticated canonical attestation of the exact blocker digest, hold sequence, Goal generation and target binding, with an opaque content-addressed evidence reference and expiry. Caller booleans, free-form evidence bodies, wrong conditions, stale/revoked proofs and proofs for a changed HOLD refuse. This is an explicit owner attestation, not an automatic validator of external decision/input truth. External satisfaction adapters are not implemented; they cannot implicitly clear a hold.

All transition commands supply the Goal generation, state, sequence and recorded session/generation. Replay first checks current authentication, binding and generation. Within that generation it returns the original immutable receipt and reconstructed original snapshot, not a historical receipt paired with current state. Changed transition/create ID reuse refuses. Old-generation replay after reopen/adoption explicitly conflicts, including old create requests. Reopen and explicit owner adoption increment Goal generation and preserve prior receipts. Worker progress never silently rewrites a Goal's session binding.

## Persistence and binding migrations

Every CompanyStore writer holds a kernel flock across reload, validation, CAS and fsync/rename. Reads refresh canonical state. Dead processes release the lock without deleting a lock inode. Queue, record, receipt, evidence, grant, proof and Goal-byte budgets are bounded. Credentials and expiring verification/unblocker authority are rechecked before the rename after temporary-file sync. A crash after commit but before acknowledgment is reconciled by the same idempotency key and receipt; it is not blindly repeated.

Rebind reserves a monotonically increasing employee generation and persists a migration fence before awaiting room migration. Both old and prospective sessions are denied Goal authority while that fence exists. Success commits only the exact reserved migration/session/generation. Failure never decreases or reuses that generation, never overwrites a separately changed binding, and leaves prior Goal bindings unchanged. Goals require explicit owner adoption before a new session can mutate them. A process crash with an unresolved migration stays fenced; automatic reconciliation and effects are deliberately absent.

## Read/privacy boundaries and compatibility

Current full records are visible only to the authenticated company owner and the current assigned worker. The same full-read predicate governs list, GET and every transition/adoption/replay result. Full command results carry `visibility: 'full'`, the coherent historical Goal and its full receipt. A VERIFY-only employee receives `visibility: 'verification'`, a closed Goal ID/binding/generation/state/sequence/time view and a closed decision receipt containing only IDs, actor/operation/state enums and times/sequences. It contains no objective, next action, creation/history snapshots, blocker prose, evidence, input digest, request digest or receipt `after` snapshot. Exact replay rechecks current credentials/grants/fences before returning the same historical closed view. A METADATA_READ grant never upgrades this view to full. No separate full-read grant is implemented.

Team metadata requires a separate owner-issued target/reader binding grant. Metadata contains fixed identifiers, generation/state/category/binding enums and times/sequences; it excludes objectives, blocker prose, next actions, evidence, receipts, paths, prompts and transcripts. Human-facing text remains in the separately scoped canonical full record. Evidence references are bounded content digests rather than paths or bodies.

Existing company records with no Goals migrate through schema defaults. This unreleased successor does not invent missing historical snapshots or proof for nonempty pre-release r1 Goal records; those require an explicit reviewed migration before activation. The original r1 packet and its independent review remain unchanged. Source and synthetic acceptance do not establish a deployment, complete effect integration, crash-reconciliation operator path, full-suite pass or permission to activate.
