# Resource replacement restart recognition

The resource result route can recognize an operation which already completed
through the canonical native settlement path before the website restarted.
Every website process initially treats saved resource records as recovery-required.
Recognition uses a new current-owner preview context on the protected resource
channel. It restores no execution context, journal handle, startup permit or
previous approval session.

The fixed host inspection holds the existing global admission lock. It reads the
accepted operation journal and its canonical settled and verified receipts,
checks that no settlement marker or conflicting employee operation remains,
and binds all historical plan references. It observes the current exact target
container, effective limits, employee home/Nix/scratch and account roots, actual
capacity and current policy. The first supported case requires the approved
target SID and generation still to be current and running, with the exact
settled container ID and profile. A later plan move, stopped target, pending,
missing receipt, source-only completion assertion or unknown fact refuses.

Kernel/capacity/storage work precedes the final complete native inventory bracket.
Final canonical metadata reads include their descriptor cleanup and anchored
file/ancestry stamps. The inspection checks those stamps again after admission
cleanup. It never changes operations, profiles, receipts, markers, native state
or capacity accounting. The private TypeScript settlement object can only come
from the real resource client and a current owner context. After the website
metadata save it repeats the read-only host inspection and compares its exact
historical/current binding. A refusal or lost acknowledgement leaves the record
recovery-required. Another restart requires another fresh inspection.

These checks serialize cooperating broker operations. They do not make arbitrary
external mutations after each final observation atomic. Historical recognition
does not prove a resumed conversation, authorize incomplete-operation recovery,
or establish fresh CLI readiness. Native acceptance and incomplete/cancelled
operation reconciliation remain separate gates.

Website facts are loaded per protected Q connection, never eagerly by Broker
construction. Missing or stale actor facts refuse that channel while ordinary
existing laptop/phone recovery remains available under its original reservation
guards. Each executing connection retains its original facts and refuses their
replacement or an installer marker; it never silently adopts refreshed facts.
Refreshing installed facts is an explicit owner-local installer workflow under
the same admission/custody rules. This source does not perform that workflow or
install, restart, wake or resize a laptop.
