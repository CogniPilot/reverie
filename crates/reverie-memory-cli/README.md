# Installed memory bridge candidate

`reverie-memory` reads one path-free screen/recall/remember JSON request from
stdin. Instance selection belongs to the installed bootstrap (`--instance` or
`REVERIE_INSTANCE_CONFIG`), not the request. This candidate is not selected in
the runtime package. Namespace observations and installed configuration do not
authenticate a caller or grant access to another employee or project.

Recall requires explicit initialization. Missing state returns NotInitialized;
recall does not import, seed, create profiles, reembed, or repair a selected model.
`--initialize` is the explicit, idempotent lifecycle operation. The real launcher
must establish its authenticated employee/project scope and call startup before
runtime selection. Startup and recall share actual namespace checks and a fixed
flock; this does not coordinate legacy Python writers during a split cutover.

Remember applies the same qualified fixed private-person floor, then invokes the
supported `reverie agent journal save` API client in its captured session. Room,
turn, quote/reference and tag come from the request; nothing guesses a source.
No direct write to the legacy memory database is used. A missing session/source
returns a copyable command. A lost or malformed post-dispatch reply is an
unconfirmed save, never “nothing was saved,” and is not automatically retried.
Native client cleanup finishes before response publication. Process uncertainty
retains the same actual client rather than starting another one.

Configured owner regex patterns remain a required compatibility dependency.
This candidate refuses a nonempty rule set until a Python-compatible native
adapter is independently qualified; it never silently omits rules or substitutes
a different regex language. The fixed floor uses shared frozen Unicode facts and
actual Python differential fixtures, not an arbitrary regular-expression VM.

Intentional corrections needing review before selection: request fields are
closed (no path/model/private-store editor); read-only recall and journal saves
do not trigger hidden ChatDaemon startup mutations; journal success requires the
actual success/data envelope; lossless JSON responses escape surrogate codepoints
instead of failing on stdout encoding. Existing Office journals remain distinct
from the legacy employee/project memory tables and Handsroom data.

The journal transport uses the common retained process owner. Its 60-second,
8 MiB combined transport policy is separate from embedding HTTP semantics and
the broker metadata capture policy. Actual supported Rust/TypeScript journal
client packaging, launch/auth binding, configured endpoint-scheme inventory,
owner-regex compatibility and coordinated single-writer cutover remain required.
Synthetic child fixtures prove transport/cancellation/refusal behavior; they do
not prove API authentication, a live save, or a completed company migration.
